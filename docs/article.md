Signalcraft is a small app where a group adopts **Scrap**, a salvaged robot who runs on signal. Every honest check-in from a member keeps him powered. Overnight, while nobody is watching, he writes a short log entry about the day in his own voice, and it is waiting in the morning. I built it solo over one weekend for the AWS Builder Center Weekend Creative Agent Challenge, on top of Undercurrent, the app I shipped for the Full Stack Challenge two days earlier.

One rule defines the whole thing: **Scrap is powered by honesty, not by happiness.** A terrible day powers him exactly as much as a great one. He only runs low when nobody says anything at all. He never dies; with no signal he powers down and sleeps, and he wakes the moment someone checks in.

## The vision

Most "mood" apps quietly reward people for reporting good days. Signalcraft refuses to. Scrap does not care whether you had a good day; he cares whether you said so. That turns participation into the only currency, which is the one thing a group can actually control.

The second half of the idea is the agent. Scrap is not a chatbot you poke. He acts on a schedule, alone, with no user in the loop: every night an EventBridge Scheduler wakes a Lambda, the Lambda reads the day's aggregates, asks Claude Haiku 4.5 on Amazon Bedrock for three to five sentences in Scrap's voice, and stores the entry keyed to the date. Nobody triggers it. You just find it in the morning, which is the part that makes him feel like he lives there.

Two honesty notes about this build, because the app is about honesty:

- **It is a concept build with a seven-day life.** The footer says "concept build — running through Sun Aug 30, 2026." After that I disable both schedules (the nightly log and the hourly power tick) and delete the Amplify app. An unattended nightly job is the failure mode for a hackathon project, so the ending is planned, not forgotten.
- **The demo group's log history is seeded.** Entries for Aug 18–22 were generated by `scripts/backfill-log.ts`, which runs the same Bedrock generator against five days of synthetic aggregates so the archive looks lived-in from day one. Same prompt, same model, fake inputs. The first autonomous entry is scheduled for 00:30 ET on Aug 24 (dayKey 2026-08-23). ## How I built it

I started from a working codebase and a written spec. Undercurrent already had Amplify Gen 2, Cognito with groups, AppSync and DynamoDB with subscriptions, a Python Bedrock Lambda, CI/CD, theme tokens, and a Canvas 2D river. Signalcraft reuses all of that and adds four things: a clock (EventBridge Scheduler), a power meter (a Lambda on the `PingReceipt` stream), a character, and a date-keyed log.

**Deploy first.** Step one was a fresh clone with the remote swapped, a new Amplify app, and a green build with its own URL before touching a feature. [TODO: how long the first deploy took and whether the npm ci lockfile fix from Undercurrent carried over cleanly.]

**Prove the riskiest wire second.** Undercurrent never shipped a scheduler; EventBridge was cut from its tier 3. So the nightly tick was genuinely new and the first thing I proved: set it to every five minutes, watched a real entry land in DynamoDB, then switched it to nightly. [TODO: what actually broke here, from NOTES.md.]

**The check-in flow carried over wholesale, and it is the best decision in the codebase.** A check-in writes two rows: `Ping` carries a score and no author; `PingReceipt` carries an author and a day key and no score. The schema physically cannot leak what it never stored. For Signalcraft this split did more work than I expected: Scrap's power is computed from `PingReceipt` only, unique members in the rolling 24-hour window, by a Lambda that never reads `Ping`. The rule "honesty, not happiness" is not a comment in a function. The table that powers Scrap does not contain a mood column.

**Scrap is drawn in code, not generated.** He is SVG in React with named parts (body, head, face plate, eye, antenna, chest light, arms), so the five power states are attribute changes, not five image files. I considered generating him with an image model and decided against it: image models drift, and by night four a generated Scrap would be a slightly different robot, which reads as a bug. Code-drawn means perfect consistency, cheap state changes, CSS-variable fills so he re-tints with the light/dark theme, and `prefers-reduced-motion` for free. Bedrock writes what is *around* him: the log. It never draws him.

## AWS services and architecture

```
check-in  ->  AppSync (userPool)  ->  DynamoDB: Ping + PingReceipt
PingReceipt stream  ->  compute-power Lambda  ->  Robot row (AppSync mutation, so subscriptions fire)
EventBridge Scheduler (nightly)  ->  Python 3.12 Lambda  ->  Bedrock Converse (Haiku 4.5)  ->  LogEntry (dayKey)
Browser: React + Vite, Amplify Data subscriptions, SVG Scrap + Canvas 2D scene
```

- **AWS Amplify Gen 2** provisions everything from TypeScript: Cognito auth with `lead`, `member`, and `dev` groups; AppSync GraphQL with DynamoDB; Lambdas; Amplify Hosting with CI/CD from GitHub.
- **Amazon EventBridge Scheduler** runs two schedules: the nightly log at 00:30 America/New_York — the reason this counts as an agent, the only component that acts without a user present — and an hourly power tick that recomputes Scrap's power, because check-in receipts never expire and without it he would never power down.
- **AWS Lambda**: a Node function on the `PingReceipt` table stream computes the five power states and publishes a `Robot` row through an AppSync mutation, which is what makes every open browser's Scrap change at once. A Python 3.12 function, boto3 only and no bundling, is the nightly writer.
- **Amazon Bedrock**, Claude Haiku 4.5 through the `us.` cross-region inference profile. Opus and Sonnet tiers are sales-gated on this account, and Haiku is plenty for five warm sentences. Cost guards are structural: one call per group per night, hard-capped, low `max_tokens`, and an AWS Budget alarm at $5 turned on before the schedule was enabled.
- **Amazon DynamoDB** holds one `LogEntry` per group per day, never overwritten. Nothing in this build reads history beyond the archive view, but storing it date-keyed now is what makes memory features possible later. It costs one composite id (`teamId#dayKey`) and a conditional write.

## What I learned

- **Enforce a rule in the data model, not in a comment.** "Mood never affects power" is true because the power Lambda reads a table with no score column. A reviewer can check that in thirty seconds.
- **A scheduled job is a different kind of code.** Nobody is there to see it fail. Proving it at five-minute cadence first, then the budget alarm, then the teardown date in the README, is the whole discipline.
- **Consistency beats generation for a character.** The most "AI" choice, generating Scrap, would have made him worse. Use the model for what changes nightly; draw what must stay the same.
- **Seeded history is fine if you say so.** The backfill made the demo readable and the article honest at the same time, because the disclosure is part of the product.
